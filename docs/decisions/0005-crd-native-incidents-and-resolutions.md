# ADR-0005: Incidents and remediation are Kubernetes CRDs, agent-owned, synced from server

**Status:** Accepted — the apply step described below is superseded by [`ADR-0007`](0007-agent-never-applies-remediation.md); the CRD-native design (three reconciler loops, spec/status ownership split) is unchanged.
**Related:** reads [`ADR-0001`](0001-server-agent-operator-split.md), [`ADR-0003`](0003-human-in-the-loop-remediation.md), [`../concepts/finding-and-incident.md`](../concepts/finding-and-incident.md), [`../concepts/remediation-flow.md`](../concepts/remediation-flow.md); affects [`../components/agent/README.md`](../components/agent/README.md), [`../components/server/README.md`](../components/server/README.md), [`../api/crds.md`](../api/crds.md)

## Context

v0.1 shipped `Incident` and `RemediationProposal` as REST-only objects living in talam-server's history store, with the agent polling talam-server for approved proposals and applying them directly. That's workable, but it means `kubectl` has no view into remediation state, and there's no way to reconcile an approved fix declaratively the way the rest of Kubernetes works — a proposal's "approved" state was a row in a store, not a spec a controller could watch.

The ask is to make both first-class CRDs — `MeshIncident` and `MeshResolution` (the CRD realization of `RemediationProposal`) — with `MeshResolution` referencing its `MeshIncident`, a controller that reconciles a resolution (applies it once manually triggered) and reports status on the object itself, and `MeshIncident` watching its resolutions to mark itself complete once all of them have been performed. Trigger stays manual, controlled through the UI, per [ADR-0003](0003-human-in-the-loop-remediation.md).

The complication: [ADR-0001](0001-server-agent-operator-split.md) draws the trust boundary specifically so talam-server never needs Kubernetes credentials into any spoke cluster — it can run entirely outside Kubernetes, and agents only need outbound reachability to it, never the reverse. Naively letting talam-server create/update CRDs in every cluster it manages would mean handing it a credential (or kubeconfig) per spoke cluster, which is exactly the blast-radius expansion ADR-0001 was written to avoid.

## Decision

The CRDs live in the cluster the agent already manages, and the **agent remains the only writer there** — no new credential is handed to talam-server. talam-server stays the source of truth for cross-cluster history and the only component that calls an LLM (unchanged from ADR-0001/ADR-0002); it doesn't create or mutate any CRD.

Three loops run in talam-agent instead of the old direct-apply poller:

1. **Sync** pulls `GET /v1/incidents?cluster=X` and `GET /v1/proposals?cluster=X` from talam-server (both already support cluster filtering) and creates/updates local `MeshIncident` / `MeshResolution` objects to mirror them — including mapping a server-side proposal's `Approved` state onto the resolution's `spec.triggered: true`. This is the only place server state ever reaches the cluster, and it's a pull, not a push.
2. **Resolution reconciler** watches local `MeshResolution` objects for `spec.triggered == true` with a still-pending status, and is the thing that actually dry-runs and applies (reusing the same resourceVersion-gated apply path introduced after the independent review — see the PR description), writing the outcome into `status` and reporting it back to talam-server (`POST /v1/proposals/{id}/outcome`) so the durable history stays accurate.
3. **Incident reconciler** watches local `MeshIncident` objects, lists the `MeshResolution` objects referencing each one, and marks `status.complete = true` once every referenced resolution has been **performed** — defined as reaching `Applied` or `Failed` (an apply was actually attempted). A `Rejected` resolution does *not* count as performed: rejecting a fix is a decision not to act, and the incident should stay visibly incomplete until something is actually done about it, not silently marked done because a human said no.

The manual-trigger-via-UI requirement is satisfied without the UI (or talam-server) ever touching Kubernetes directly: the dashboard's Approve button still only calls talam-server's existing REST decision endpoint, exactly as before; the trigger reaches the CR through the Sync loop's next pull. `kubectl patch` against `spec.triggered` directly also works as an escape hatch — a useful side effect for the GitOps-style approval mode already on the roadmap — but the dashboard remains the intended path for v0.1.

## Consequences

`kubectl get meshincidents` / `kubectl get meshresolutions` now show live remediation state without hitting talam-server, and the actual apply decision is a genuine reconciliation loop watching a spec field, not a REST poll branching on a store's row state — closer to how the rest of the system (the operator watching `MeshDiagnostics`) already works. No component's trust boundary changes: talam-server still never needs cluster credentials beyond its own (for `ModelBinding`), and the agent's blast radius is unchanged (it already had RBAC to apply these patches).

The cost is a sync lag: approval in the dashboard doesn't flip `spec.triggered` until the next Sync tick, not instantly — acceptable for a human-approval workflow where the round-trip already involves someone reading a proposal, but worth knowing if a tighter UI feedback loop is ever wanted (the dashboard already polls every 5s, so in practice the two loops mostly overlap). Cross-cluster incident correlation (an incident whose findings span two clusters) doesn't fit this model cleanly — a `MeshIncident` CR lives in exactly one cluster, so for now it's created in whichever cluster talam-server's incident's findings originated from. Real cross-cluster correlation is v0.2 scope regardless ([roadmap](../architecture/overview.md#roadmap)); when it lands, a cross-cluster incident likely needs a server-side-only representation with per-cluster `MeshIncident` objects as satellites, which is a problem for that ADR, not this one.
