**Status:** Accepted
**Related:** reads [`ADR-0001`](/docs/decisions/0001-server-agent-operator-split/), [`ADR-0002`](/docs/decisions/0002-deterministic-analyzers-then-llm/); affects [`../components/server/README.md`](/docs/components/server/), [`../concepts/object-model.md`](/docs/concepts/object-model/)

## Context

Analyzer evidence is a point-in-time snapshot, and it's necessarily narrow — [ADR-0002](/docs/decisions/0002-deterministic-analyzers-then-llm/) keeps analyzers pure (no network calls), so a `Finding`'s `RawEvidence` only ever contains what the collector already had in the `MeshSnapshot`. An explanation would often be sharper with more: recent error-rate history for the affected workload (a metrics backend), live pod/container status beyond what the collector snapshotted (a Kubernetes backend), or a fresh Envoy config dump / mTLS posture check that's expensive enough that no analyzer should run it every scan tick (a service-mesh-specific backend). [MCP](https://modelcontextprotocol.io) is the natural fit for "let the LLM gateway reach these" — it's already how tool access is meant to be composed.

The risk is architectural, not technical: if the *LLM* decides at explain/propose time which MCP tools to call and with what arguments, detection has quietly moved back into the model. That's exactly what ADR-0002 was written to prevent — a missed failure mode becomes a prompting problem instead of a missing analyzer, non-deterministic, and much harder to test. Tool outputs would also become part of the trusted prompt context sight-unseen, which is a real prompt-injection surface once anything past our own collectors can populate it (a metrics label, a pod annotation).

## Decision

MCP tool calls are **server-initiated and deterministic**, not agentic. Talam-server maintains a small, explicit table keyed by `Finding.AnalyzerID` (e.g. `peerauth.mtls-mismatch → [mesh.get_mtls_status]`) that says which MCP tools to call and how to build their arguments from the finding's own `Resource`/`RelatedRefs` — the same kind of static mapping an analyzer's own logic already is, just running server-side because MCP servers may not be reachable from every agent's more restricted network position. The LLM never sees a tool definition and never decides to call one; it only ever receives more evidence in the same JSON blob it already explains from (`internal/server/llm`'s `incidentEvidence`), gathered *before* the Explain call, not during it.

Registering an MCP server is itself an object — `MCPServer` (namespaced, watched by talam-server, same poll pattern as [`ModelBinding`](/docs/api/crds/#modelbinding)) — carrying an endpoint, optional auth, and a `toolset` tag (`metrics` | `kubernetes` | `mesh` | `custom`) the enrichment table's entries reference generically rather than hard-coding a specific server name. Off-the-shelf MCP servers (a Prometheus-backed metrics server, a Kubernetes server) are expected to be run independently and just registered by URL. The one this repo builds and owns is `talam-mesh-mcp` (`cmd/talam-mesh-mcp`) — a purpose-built, read-only server exposing Istio introspection (DestinationRule/VirtualService/PeerAuthentication state, mTLS posture) that nothing generic would provide, deployed per-cluster next to the agent, reusing the same dynamic-client read patterns `internal/collect/istio` already has.

That per-cluster placement matters for the same reason [ADR-0001](/docs/decisions/0001-server-agent-operator-split/) draws the line where it does: `talam-mesh-mcp` needs live read access to one specific cluster's mesh state, so it runs *in* that cluster with the agent's kind of scoped, read-only RBAC — never talam-server's own credentials. What's new here, and worth naming plainly rather than letting it slide in quietly: talam-server now needs *network reachability into* that cluster (an MCP endpoint it calls), which is a connection direction nothing before this ADR required (agents only ever call *out* to talam-server). This is deliberately narrower than a Kubernetes credential — talam-server gets exactly the handful of read-only tools `talam-mesh-mcp` chooses to expose over HTTP, not raw API server access — but it is a new crossing, and it means `talam-mesh-mcp` must be reachable from wherever talam-server runs (a `Service`, exposed however the cluster's network topology allows — ingress, NodePort, a VPN — same problem any operator already solves for exposing a read-only status service, not a new one talam invents).

## Consequences

Evidence gets richer without detection quality becoming a function of model behavior — a missing enrichment call is a config gap in the analyzer→tool table, debuggable and testable exactly like a missing analyzer, not a prompting problem. The LLM's job stays exactly what ADR-0002 already said it was: explain and propose from evidence it's handed, now just more of it. The cost is the new reachability requirement above, and one more object type (and one more binary, for the mesh-specific server) to deploy and keep healthy — accepted because the alternative (agentic tool-calling) trades a deployment problem for a much harder trust and testability one.
